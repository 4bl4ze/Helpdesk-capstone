What these are

The ten wireframe screens, rebuilt in the real design system. Every element inside a device frame is a ds- class from desktrace.css — nothing is drawn specially for this page. That makes these mockups a working test of the system: four components were missing when I started (data table, photo slots, chart rows, hero figure) and were added to the system rather than faked here.

The wireframes carry the reasoning for why each screen is laid out this way. These show the result. Screen numbers match, so S06 here is S06 there.

Pausing stops the resolution clock

  • Device history sits above the fault report. The most consequential ordering decision in the set. The proposal's own scenario has a technician seeing that the projector failed twice this term — worthless three scrolls down. This is what makes the register useful to a technician rather than only to an auditor.
  • History entries carry their resolution, not just the fault, so the next technician can skip a diagnosis.
  • "What did you check or change?" not "Notes". A box labelled Notes produces "fixed". Next term's repair history is decided by the wording of this one label.
  • Two actions, weighted 2:1. Resolve is the common case. Pause states its consequence, because the technician is stopping a measured commitment.

  • One hero figure, then stat tiles. A dashboard leads with a single number — SLA compliance is the one the manager is judged on. The wireframe had six equal tiles; six equals means no hierarchy, so the eye reads all six to find the important one.
  • Every tile carries a delta against a named period. "3 at risk" is a fact; "up 2 vs last week" is information.
  • Horizontal bars, one series, no legend. Category names here are words, not dates, and horizontal bars give a label room to be read instead of rotated. One series means the title already says what is plotted, so a legend box with one swatch would just restate it.
  • The series colour is the accent, never the SLA colours. Green, amber and red are reserved for state. If a bar chart used them, "red" would stop meaning "breached".
  • Repeat faults keep their exact counts beside the bars. This is the proposal's "Learn" pillar and its stated business outcome — the manager takes these rows to a budget meeting, and a rank you cannot quote is no use there.
  • The dashboard ends in actions. A dashboard that only reports leaves the manager hunting in another tab for the thing it just alarmed them about.

What building these changed in the design system

Mockups are the first real test of a design system. Four components were missing and got added rather than faked, and three existing decisions turned out to be wrong:

ChangeWhy
Added .ds-tableS08 and S09 are table tasks. Bulk audit and comparison is not a card job.
Added .ds-uploadThree fixed photo slots, so FR-TKT-01's limit is layout rather than an error message.
Added .ds-chartThe dashboard needed a chart primitive that the real Chart.js build can mirror.
Added .ds-hero, .ds-kpi__deltaA dashboard leads with one number, and a figure without a comparison is not yet information.
Fixed: KPI figures were tabularTabular figures give every digit a zero's width — fine in a column, loose and gappy at 40px. Tabular now belongs to tables, timestamps and the ticking countdown only.
Fixed: meter track was always neutralThe unfilled track now takes a light step of the fill's own ramp, so an at-risk state reads across the whole bar instead of only the filled part.
Fixed: six equal KPI tilesSix equals means no hierarchy. One hero plus four tiles says which number matters.
